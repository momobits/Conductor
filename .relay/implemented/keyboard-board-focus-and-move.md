# Keyboard board focus & move chord (Phase 17 #41)

## Summary

*Resolved: 2026-05-16*

- **Goal:** add roving keyboard focus to the Board view (column-focus via `1..7`, walk tiles via `↑/↓`, walk columns via `←/→`, `Home`/`End`, `Enter` to open) plus a move chord (`M` then `1..7`, or `Shift+M` one-shot) with combined column-highlight + footer-banner UX feedback. Close the keyboard-only path through the kanban workflow that Phase 25.1's dispatcher set up.
- **Approach:** pure `decideBoardAction(ev, state) → Action` + DOM-wrapper split (n=10/11 pure-helper-extraction precedent — `decideBoardAction` + `resolveArrowAcross`). New `src/ui/views/board_keys.ts` exports the dispatcher; `renderBoard` calls `attachBoardKeys` once on first paint and `syncFocusAfterRepaint()` on every subsequent paint (focus survives SSE re-renders). Synthesized from 5 parallel /relay-superplan strategy agents (Minimal Change, Performance-First, Safety-First, Refactor-Forward, Test-Driven) — base was Refactor-Forward, cherry-picked Performance-First's `::before` CSS targeting (a load-bearing correctness fix only that agent caught), Safety-First's `disposed` flag + modifier hygiene + URL-injection guard + `cssEscape`, and Test-Driven's plain-data `BoardSnapshot` parameter.

## Caveats

- **Implementation deviation documented in feature spec:** the move-mode "any other key exits" branch in `decideBoardAction` was tightened with a `noMods` gate during Step 7's test run. Without the gate, `Ctrl+1` would have exited move mode rather than no-op'd — a confusing UX when the user is invoking a browser shortcut. The fix preserves Safety-First's modifier-hygiene principle (already applied throughout the rest of the function) and aligns with the spec's "any other [unmodified] key exits" reading. `'8'` in move mode still exits (unmodified, per spec); `Ctrl+1` now correctly returns `noop`.
- **Move mode forward edge for the kanban gateway was nearly broken.** The adversarial review surfaced that `lib/keys.ts:57-67` was firing `1/2/3 → navigateTo(...)` BEFORE delegating to `boardKeyHandler`, so move-mode `1/2/3` would have been intercepted by view-switch (no-op hashchange) and never reached `attempt-move`. The plan documented this as "Low UX" — actually CRITICAL since it blocked the two most common forward transitions plus three legal backward edges. The fix (Step 4) extends `KeyContext` with `boardInMoveMode: () => boolean` and gates the view-switch; verified by 1 new assertion in `keys.test.ts`.
- **Normal-mode `1/2/3` for column focus remains intercepted by view-switch.** Operators arrow-navigate or use `4..7` to focus columns 4-7 directly. Fixing this would require another gate (e.g., `boardWantsColumnKey(n)`) — more invasive, deferred. Acceptable: the keyboard layer is operable via arrows + `4..7` + `M`; the original UX gap remains for `1/2/3` column focus only, not for any move target.
- **Manual smoke not exercised in browser this session.** The verification report documents the planned smoke matrix; operator validation deferred to session-end or next session.
- **`confirmTransition` and `shakeTile` exports are short-lived.** Phase 25.3 (`keyboard-approval-dialog-bindings`) will extract both transition-approval dialogs into `src/ui/lib/dialog.ts`; the export from `board_dnd.ts` goes away at that point, replaced by an import in both `board_dnd.ts` and `board_keys.ts`. Doc-comments on the exports flag this.
- **Pattern precedent advanced** — pure-helper-extraction at n=9 (Phase 25.1) now lands `decideBoardAction` + `resolveArrowAcross` + `isInFormField` (the latter already counted; `decideBoardAction` makes n=10, `resolveArrowAcross` makes n=11). NEW variant precedent: "shared validator module for cross-feature consumption" (Phase 24 `board_validate.ts` designed for this feature) — now demonstrated end-to-end. ADR filing remains deferred per operator decision in STATE.md.
- **`shakeTile` restart fix benefits drag-drop too.** Phase 24's archived issue `ui-board-dnd-invalid-transition-uses-server-error-alert` had a latent restart-safety bug (`classList.add` is a no-op if class already present, so rapid repeated illegal drags wouldn't re-shake). Fixing it in this feature's Step 1 export propagates to the existing drag-drop path. Not a regression — improvement.
- **No notebook** — `relay-config.md § Notebook Setup` skips notebooks for this TypeScript-only project.

## Adversarial review trail

Multi-agent /relay-superplan synthesis caught two issues the base plan (Refactor-Forward) and 3 of 4 sibling strategies missed:

1. **CSS `::before` targeting** — Performance-First was the only agent to note that `.column[data-num]` is an *attribute* on the section, not a child element; the visible numeral is rendered via `.column::before { content: attr(data-num); }` at `app.css:326-339`. The other 4 plans targeted `[data-num]` as a descendant selector (matches nothing). Synthesized plan adopted Performance-First's `::before` insight.

2. **Move-mode dispatcher pre-emption** — adversarial review (post-synthesis) caught that `lib/keys.ts:57-67` fires `1/2/3 → navigateTo` before delegating to `boardKeyHandler`, blocking the kanban gateway transitions in move mode. None of the 5 strategy agents flagged this during their initial planning; surfaced only by the explicit `/relay-review` adversarial pass. Fix added as Step 4 of the revised plan; verified by 1 new test assertion.

These two findings illustrate the value of the multi-agent + adversarial-review pipeline: diversity of perspective catches correctness issues a single planner would miss, and the adversarial gate catches structural integration issues that single-feature planning glosses over.
