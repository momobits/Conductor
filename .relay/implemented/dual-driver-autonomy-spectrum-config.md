# Implemented: Dual-Driver Autonomy Spectrum Config

## Summary

*Resolved: 2026-05-24*

**Problem**: Phase 22's dual-driver cluster shipped #54 (orchestrator-core) with a typed `OrchestratorDecision` contract, but #54's executor (in #6/#59) needed a project-default autonomy spectrum (`assist | hybrid | autonomous`) to gate its execute-vs-surface decision. The existing schema's `autonomy.transitions.*` per-edge config (each transition `manual | assist | auto`) is the wrong granularity for the orchestrator-driven model — the orchestrator decides what op to call, when to advance, when to halt; tuning "the policy for the `discovered_to_planned` transition specifically" doesn't fit. The spectrum tunes the orchestrator's risk tolerance per card. Without this feature, #6/#59's executor would have to hardcode one mode; #62 frame-b-chat-wire (1 in-cluster dependent) consumes the spectrum directly to dispatch chat messages per autonomy mode.

**How it was resolved**: New sibling module `src/conductor/autonomy.ts` (precedent: protocol-extraction pattern from #55 `lead.ts`, #58 `substrate_hygiene.ts`) exposes four pure helpers: `mapLegacyAutonomy` (card-level legacy → spectrum), `effectiveAutonomy(card, config)` (card override vs project default resolution), `autoExecuteThreshold(mode, config)` (executor gating shape per mode), and `bridgeSpectrumToConductMode` (spectrum → legacy ConductMode for the existing `conduct.ts` path). Project-default schema rewritten: `autonomy.default` now uses `AutonomyModeSchema` (3-mode enum exported from `schema.ts`), accompanied by `hybrid_confidence_threshold` (0.7 default) and per-mode `budgets.{assist,hybrid,autonomous}.{orchestrator_calls_per_card, observer_calls_per_minute}`. Legacy `transitions.*` block is kept optional in the schema for backward-compat with consumers that still read it (`lifecycle.transitionPolicy`, `board.ts`, `board_dnd.ts`).

A zod `.preprocess()` shim on the `autonomy` block detects legacy shapes at load time and rewrites them to spectrum: `'escort'` → `'assist'`, `'auto'` → `'autonomous'`, `'critical'` → `'autonomous'`; missing default + `transitions` block present → infer from majority (mostly `'auto'` → `autonomous`, mostly `'manual'` → `assist`, mixed → `hybrid`). A module-level flag (`sawLegacyAutonomyShape()`) is set by the preprocess; consumed by `src/config/load.ts` to emit a one-time deprecation warning on stderr. Card-frontmatter `AUTONOMY_MODES` enum is widened **additively** (preserves all 4 legacy values + adds `'hybrid'` / `'autonomous'`) so existing card files continue to parse without rewrites.

Every callsite that hardcoded legacy mode lists was updated to accept both shapes: `src/cli/commands/autonomy.ts` (CLI accepts spectrum + legacy with deprecation warning, writes spectrum to disk), `src/daemon/mcp_server.ts` (tool description), `src/rpc/schema.ts:ConductorSetAutonomyParams` (z.enum widened), `src/ui/views/routing.ts` (dropdown shows 3 spectrum modes; YAML serializer + parser handle optional `transitions` + `hybrid_confidence_threshold`), `src/cli/commands/init.ts` (default template emits new shape only). `src/conductor/loop.ts:effectiveMode()` now bridges spectrum → ConductMode via the new helper, preserving `conduct.ts` semantics for the existing pre-orchestrator (#6/#59) decision path.

**Pattern precedent**: pure-helper extraction reaches **n=18** with this feature's four `autonomy.ts` helpers + the schema preprocess function + the loader's once-per-process warning latch. ADR filing remains operator-deferred per `feedback-adr-scope-discipline.md` memory.

## Caveats

- **Cost-guard `checkOrchestratorCallCeiling` deferred** — spec proposed adding this in `cost_guard.ts`, but the per-card orchestrator-call counter doesn't exist in `RuntimeStore` yet. Adding it cleanly requires extending the runtime interface (new `incrementOrchestratorCalls(cardId)` + `getOrchestratorCallCount(cardId)`) which is out of scope for this feature (the executor in #6/#59 will need to call it; without a live caller, dead-code introduction violates auto-mode's no-drive-by-changes rule). Per-mode budget values ARE serialized in config; consumers (future #6/#59) read them directly via `config.autonomy.budgets.<mode>.orchestrator_calls_per_card`. Filed inline as Implementation Deviation #1 in the spec file.
- **`config.confidence.threshold` and `config.autonomy.hybrid_confidence_threshold` both exist** — `confidence.threshold` (default 0.7) is consumed by the existing `conduct.ts` path (preserved for backward-compat). `autonomy.hybrid_confidence_threshold` (default 0.7) is consumed by the new `autoExecuteThreshold` helper. Both kept; unification opportunity for v2 noted in the deviation. Operator-tunable independently.
- **Critical's halt-on-low-confidence semantic relaxed** — legacy `'critical'` mode would halt the conductor queue when decision confidence dropped below threshold (per `conduct.ts:60-62`). The spectrum has no equivalent; `'critical'` maps to `'autonomous'`. Operators relying on halt-on-low-conf behavior must either pin `autonomy.default: 'assist'` (every decision surfaces) or rely on the future executor's pending-decision flow. Documented in the spec's Implementation Deviation #3.
- **Card frontmatter enum kept widened, not narrowed** — the spec hinted at mapping card-level legacy on read. We achieve the same effect by keeping `AUTONOMY_MODES` additive and applying `mapLegacyAutonomy` inside `effectiveAutonomy`. Avoids rewriting all existing dogfood card files; preserves auditability of pre-Phase-30 card autonomy choices.
- **`autonomy.transitions` block kept readable post-migration** — schema preserves `transitions` as optional after migration so a partially-migrated config doesn't fail strict-mode parse, and so consumers in `lifecycle.transitionPolicy` / `board.ts` / `board_dnd.ts` continue to work. Per-edge transition policy is effectively vestigial post-#58 (lifecycle widen) + this feature, but removing it cleanly belongs in a future cleanup pass (the UI consumers' bridge code is still readable from this base).
- **`loop.ts:effectiveMode` does NOT yet read per-card overrides** — the existing method is synchronous; reading the card would require an async readCard call. Per-card override resolution lives at the future executor's call site (which IS async) via `effectiveAutonomy(card, config)`. Marker comment in `loop.ts` makes this explicit for the #6/#59 wiring.
- **Migration warning emits via `console.warn` / `process.stderr.write`** — spec was ambiguous on the channel; chose stderr for daemon-startup visibility + CLI feedback. Daemon-startup log catches the first parse; CLI users see it during command runs. Once-per-process latch prevents spam.
- **#62 frame-b-chat-wire is the live consumer** — this feature unblocks #62 (1 in-cluster dependent); the spectrum mode + threshold helpers are ready for #62 to call when dispatching chat-as-command via the chat box's auto-dispatch logic. No coordination needed; #62 can build against the shipped surface.
- **No ADR filed.** Per operator memory note (`feedback-adr-scope-discipline.md`), pattern precedent (protocol-extraction n=3 with `autonomy.ts`; pure-helper extraction n=18 counting the 4 helpers + preprocess + warning latch) is recorded here rather than as a separate ADR. Operator-deferred per the memory.

Cohort B reasoning consumers (#56 observer-advisor, #57 lead-handoff-reconciliation) can proceed in parallel after #61.
