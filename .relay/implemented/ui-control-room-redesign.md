# UI control room redesign

## Summary

*Resolved: 2026-05-15*
*Source: User-initiated in-session redesign (no prior issue or brainstorm — UI's Phase-5 scaffold styling was the most visible "scaffold-quality" surface remaining after Phases 13-18 stabilized the engine/CLI surface).*

- **Problem**: The UI shipped in Phase 5 was functional but visually generic — system default fonts, basic flexbox grid, inline-styled feedback (`style.color = '#1a7f37'` etc.), GitHub-style color tokens hardcoded per component. After Phases 13-18 made the engine/CLI surface presentable, the UI was conspicuously scaffold-grade. Phase 18's token-URL print fixed the first-visit functional dead end; this redesign fixes the first-visit *visual* impression.
- **Resolution**: Full visual identity overhaul to an editorial / mission-control hybrid "Control Room" aesthetic. Centralized design tokens (CSS custom properties on `:root`), three typeface family (Fraunces serif display, Bricolage Grotesque sans body, JetBrains Mono), paper-grain background overlay, typeset masthead with edition stamp, numbered nav, dot-indicated status pill, footer. Each top-level view (Board, Monitor, Routing) gets a structured header (section number + lede); Monitor's brain panel decomposes into discrete metric cells with live-state indicator + timestamped log rows; Routing replaces inline-styled feedback with `data-state` / `data-ok` attribute selectors; Board adds per-column count badges and drag-target column highlighting.

## Caveats

- **Token contract is the CSS file itself.** Design tokens live as `--ink-*` / `--paper*` / `--signal` etc. CSS custom properties on `:root`. Any future theming layer (light mode, custom brand) plugs into this surface. Tokens are not yet exported as a JSON / TS artifact — they're CSS-only. Promote to ADR if a second consumer needs them (e.g. a separate marketing site or doc theme).
- **Font dependency is CDN-only.** Google Fonts `<link>` preconnect + import in `index.html` fetches Fraunces / Bricolage Grotesque / JetBrains Mono. No font fallback bundle. Offline / air-gapped daemon deployments will fall back to the `var(--f-display)` / `var(--f-body)` / `var(--f-mono)` second-level font-family entries (`'Times New Roman'`, `'Helvetica Neue'`, `'SF Mono'`/`Menlo`/`Consolas`). Acceptable for a developer tool; revisit if the project ships as an offline-first application.
- **Inline `<style>` mutations purged from `routing.ts`.** Previously the view mutated `autonomyStatus.style.color` / `errEl.style.color` directly to switch between green-ok and red-error. The new flow uses `dataset.state` / `dataset.ok` attribute selectors that CSS picks up. If future code adds another status state, define the new variant in `app.css` rather than re-introducing inline style mutations.
- **`setStatus` API changed.** From `(text, ok: boolean)` to `(text, state: 'connected' | 'disconnected' | 'failed')`. No external callers exist (only `main.ts` itself uses it) so this is a private refactor; documented here in case a future RPC-driven status update wants to plug into the existing pill.
- **Drag-and-drop visual feedback (`drag-target` class)** is additive — the underlying drop semantics in `board_dnd.ts` are unchanged. The class is purely a CSS hook; if removed, drag-and-drop still functions, just without the column highlight.
- **Phase 18 carry-forward (`--browser` flag) intentionally deferred** to Phase 20. With the UI now presentable, `--browser` becomes the natural next step. The misplaced issue file at `.relay/archive/issues/daemon-start-missing-browser-flag.md` needs `git mv` to `.relay/issues/` before `/relay-order` picks it up (per `relay-status.md` Lifecycle Integrity Warnings) — that file move is a Phase-20 prerequisite, not a Phase-19 task.
- **Filing path is unusual.** Most `.relay/implemented/` entries arrived via the full pipeline (brainstorm → design → analyze → plan → review → implement → verify → resolve). This one was user-initiated mid-session and filed post-hoc to keep Relay's history coherent. The Phase 19 docs (`README.md` + `steps.md`) are the authoritative Control-side record; this file is the Relay-side mirror for `/relay-scan` to recognize.
