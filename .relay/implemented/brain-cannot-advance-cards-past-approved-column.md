# Brain cannot advance cards past `approved` column

## Summary

*Resolved: 2026-05-23*

- **Problem**: The autonomous brain's `defaultAgentFactory` in `src/conductor/loop.ts` built `TaskAgent` instances without a `step` field. `TaskAgent`'s `case 'approved':` requires `this.step` to run the implement op, so every card the brain advanced to `approved` halted indefinitely with `'approved' requires --step <id> (one step per call).` — a message authored for the CLI caller (`conductor work <id> --step 1.1`) but visible to operators of the brain who weren't using the CLI flag. The halt also wasn't recognized by `classifyHalt`, so it surfaced as `unrecognized-error: ...` — looked like a generic crash.
- **Resolution**: Option 2 from the issue's Proposed Direction — substrate parse + git-log inspection. New module `src/conductor/step_resolver.ts` exports `resolveNextStep` which reads the latest plan substrate (`<runId>/plan.md`), parses H3 dotted-ID step headings, walks recent git log for `feat|fix|...(<phase>.<step>):` commit subjects scoped to the card's phase, and returns the first plan step ID NOT in the committed set. The return is a discriminated `StepResolution` union (`{kind:'resolved',step}` | `{kind:'no-plan'}` | `{kind:'unparseable-plan'}` | `{kind:'all-committed'}`) so `defaultAgentFactory` emits a SPECIFIC halt reason per failure mode instead of conflating them. `defaultAgentFactory` wraps construction in an async generator IIFE so it can `await readCard` + `await resolveNextStep` before building TaskAgent while preserving the `AgentFactory: (cardId) => AsyncIterable<TaskEvent>` contract. `classifyHalt` gained a `missing-step-arg` reason + pattern matching `requires --step|one step per call|no implement step resolved` so the new halt surfaces as a typed reason. The CLI path is unchanged (CLI bypasses the factory and builds TaskAgent directly with the user-provided step).

The Adversarial Review's APPROVED-WITH-CHANGES verdict was applied inline before implementation: Issue 2 (discriminated `StepResolution` union with per-variant halts) is the load-bearing design improvement; Issues 1 + 4 (explicit imports in loop.test.ts + positive post-state `column: 'building'` assertion in the integration test) are trivial polish.

## Caveats

- **Squashed merge commits bundling multiple steps**: the commit-subject regex captures the FIRST `<phase>.<step>` pair per subject. A `feat(30.1.1, 30.1.2): two-step combo` commit registers only `1.1` as done; the resolver returns `1.2` next and the implement op re-runs it. `applyDiffFile`'s create-but-exists guard rejects the re-attempt, so the operator sees a clean halt rather than corrupt state. Documented as a known limitation in the spec's Risks table; not blocking.
- **Reverted commits**: `git revert <sha>` adds a new revert commit but doesn't remove the original from `git log`. The resolver counts the reverted step as "done" and skips it on the next attempt. Operator workaround: re-commit the work or `git reset --soft` before re-running. Documented as a known limitation. Phase 22 #6's substrate-driven orchestrator (`dual-driver-brain-loop-replacement`) removes this entire codepath; no further mitigation in scope.
- **Phase 22 supersession path**: Phase 22 #6 (`dual-driver-brain-loop-replacement`) explicitly calls out THIS issue as resolved-by-supersession when it ships. It will delete `defaultAgentFactory` entirely. The new `src/conductor/step_resolver.ts` module is independent and the substrate read + git-log inspection logic can be subsumed by the orchestrator's substrate-aware `decide()` call OR deleted alongside. Forward-compatible; no rework required when Phase 22 lands. Phase 22 is 6+ sessions out per `relay-ordering.md`.
- **Phase 22 halt-categories interaction**: Phase 22 #8 (`dual-driver-halt-categories`) widens the halt taxonomy. The new `missing-step-arg` reason is a single-pattern, single-reason addition that #8's broader rebalance can subsume cleanly.
- **TS strictness deviation documented in the spec**: `simple-git`'s `DefaultLogFields.message` is typed `string | undefined`; the resolver now uses `const message = c.message ?? ''; if (!message) continue;` and `if (m && m[1] === phase && m[2]) set.add(m[2]);` to satisfy strict TS. Behavior is identical to the plan's intent (an undefined message yields no regex match, same as before).
