# Implemented: Card-detail op controls + button state machine

## Summary

*Resolved: 2026-05-24 (Control phase 30.5; Relay Phase 20 Cohort A item #48)*

- **Goal**: Replace the monolithic `Work this card` button on the card-detail view with a sidebar of per-op buttons (Analyze · Plan · Review · Implement · Verify · Resolve) plus a master `Work all`, backed by a 4-state button machine (Idle / Running / Halted-by-chat / Halted-by-assist) so the user always knows what's happening and what their click will do. Surface new `op_invoke` and `card_resume` RPCs so each op can be triggered in isolation and the user can resume a halted brain with one click. Wire card-detail keyboard shortcuts through the global dispatcher.
- **How it was resolved**: Shipped two additive RPCs — `op_invoke({cardId, op, step?})` wraps one engine op (analyze | plan | review | verify | notebook | implement | resolve) without TaskAgent ceremony, honoring cost-ceiling check + concurrent-op rejection; `card_resume({cardId})` transfers the global lead back to `'llm'` with reason=`'ui-button'` (under the dual-driver model shipped in 30.3, this is the post-supersession resume primitive — replaces the SUPERSEDED #51 `userTouched` flag). Refactored `renderCardDetail` to replace `<button id="work-btn">` with a `<div class="op-controls">` block of 6 per-op buttons + master `Work all` + initially-hidden `Continue this card`. Implemented the 4-state button machine as a pure reducer `computeButtonStates` in `card_detail_helpers.ts` so logic is unit-testable without DOM dependency; state transitions in `renderCardDetail`'s SSE handler funnel through one `applyButtonStates()` DOM updater. Extended the SSE handler to consume `lead-handed-off` events (closes Caveat 6 from #47's impl doc — previously dropped at the task-event-only guard) and `session-end` events for op_invoke single-op flow exits. Per-op column-eligibility matrix (`COLUMN_ENABLED_OPS`) per spec lines 71-79 disables buttons for non-eligible columns with explanatory tooltips. Resolve op gets a confirmation prompt (destructive — archives the card). Added `cardKeyHandler` to the `KeyContext` interface (symmetric with `boardKeyHandler`) and wired it through `main.ts`'s `dispatch()` + `keyCtx` getter; `renderCardDetail` returns a key handler that maps Z/P/V/I/F/O/W/C bare letters to the corresponding button click (respects disabled+hidden state). Extended `SHORTCUTS` + `selectFooterShortcuts('card', ...)` so the footer rotation + `?` help overlay surface the new shortcuts.

**30.4 v1 caveat closure (in-step per Control Bridge coordination requirement)**: Swapped #47's empty-state CTAs (`data-act="run"` and `data-act="re-run"` `forEach` blocks in `renderOpSectionInto`) from `rpc.call('work_card', { id: cardId })` to `rpc.call('op_invoke', { cardId, op })`. This retires the "v1: card_work placeholder" debt documented in #47 Caveat 1 — clicking "Run analyze" on an empty section now runs ONLY analyze instead of the full pipeline. `grep work_card src/ui/views/card_detail.ts` returns ONE remaining match (the `Work all` handler — correct: master pipeline still uses work_card).

## Caveats

1. **Original spec described per-card `userTouched` resume; shipped dual-driver lead-transfer instead.** The spec was authored 2026-05-17 pre-supersede; the per-card `userTouched` mechanism it described belonged to the now-SUPERSEDED `brain-halt-on-user-chat` (#51, archived 2026-05-23). Under the dual-driver model (#55, shipped Phase 30.3), lead is a global single-token (`human | llm`); the `card_resume` RPC is a thin wrapper that transfers lead back to `'llm'` with reason `'ui-button'`. The button is labeled "Continue this card" but the brain's next iteration picks the next eligible card per ordering — if this card is next, it'll be processed first. Documented in spec §Approach as "spec deviation" (architecturally correct per post-30.3 reality; matches the SUPERSEDED #51's closure narrative in `dual-driver-lead-follow-protocol.md` impl doc line 62).

2. **`Halted-by-chat` state is technically unreachable in production until Frame B #62 (`dual-driver-frame-b-chat-wire`) ships.** The state fires on `lead-handed-off` SSE events where `reason === 'user-chat'`. Today, no code path emits that combination — the `user-chat` reason is set only by future #62's chat-submit handler that calls `lead_set({to:'human', reason:'user-chat'})`. The state machine handles the future event correctly without breaking anything today. Idle/Running/Halted-by-assist branches work today end-to-end.

3. **The conductor brain does not yet consult `getLead()` before running.** The brain loop at `src/conductor/loop.ts` doesn't check lead state when picking cards (deferred to #59 `brain-loop-replacement`). So `card_resume` correctly transfers lead state but doesn't make the brain pick up work — the brain just continues whatever it was doing OR halts because the user has chatted. When #59 lands, the brain WILL consult lead state and `card_resume` becomes the full resume primitive.

4. **Concurrent brain + UI op invocations on same card are not strictly mutex'd.** `Conductor.runOneCard` does NOT call `runtime.startSession` (artifact of how Conductor wraps `agentFactory`). So `op_invoke({cardId})` would not be blocked by `getActiveSession(cardId)` check while the brain is processing that card. Mitigations: (a) brain users don't typically also click in the UI on the same card; (b) different runIds (timestamps) prevent data corruption; (c) #59 will introduce proper session bookkeeping in the orchestrator. Accept for v1.

5. **`implement` op step resolution falls back to `resolveNextStep`.** If `op_invoke({op:'implement'})` is called without an explicit `step` arg, the handler calls `resolveNextStep(repo, cardId, phase)` from Phase 29.3. If no plan substrate exists, returns `'no plan substrate — run plan op first'`. If all steps are committed, returns `'all plan steps already committed'`. UI currently has no step picker for `implement` button click — the click invokes without `step` and relies on the resolver fallback. Step picker (per spec Open Q1) deferred to v2.

6. **`resolve` op gets a confirmation dialog (review-issue-2 closure).** Plan added a `confirmTransition({from:'shipped', to:'archived', titleHtml:'Resolve and archive this card?'})` call before `op_invoke({op:'resolve'})` because resolve archives the card destructively. Column-eligibility matrix limits the resolve button to `shipped` cards only, narrowing blast radius.

7. **`#work-btn` CSS rule left as dead CSS at `app.css:904`.** No `#work-btn` element exists post-refactor; the rule is harmless but cosmetically dead. Future cleanup candidate; not a blocker.

8. **First state-machine-reducer pure helper in this codebase.** `computeButtonStates` is the first instance of a 4-state finite state machine encoded as a pure reducer in the UI layer. Pattern precedent advances: pure-helper extraction n=17 → n=18 (per the operator memory note on ADR scope discipline — ADR filing remains operator-deferred).

9. **Cross-step closure obligation FULFILLED (30.4 v1 caveat).** The orchestrator brief's cross-step coordination requirement directed this step to land the `work_card → op_invoke` swap in #47's empty-state CTAs. Both `data-act="run"` and `data-act="re-run"` `forEach` blocks in `renderOpSectionInto` are swapped. The "v1: card_work placeholder" string is gone from the codebase. Phase 30 closes Cohort A (#47 + #48) without leaving the caveat as Phase 31+ tech debt.

10. **Frame B Cohort A independence preserved.** This feature shipped without cross-cluster coupling to Phase 22 dual-driver features except for consuming the already-shipped `transferLead` primitive from #55. The `lead-handed-off` SSE consumer is the only Phase 22 surface this step touches.

11. **Downstream unblocking.** With #48 shipped, Frame B Cohort C feature #50 (`column-transition-op-triggering`) is unblocked — it delegates to `op_invoke`. Cohort B feature #49 (`chat-driven-description-authoring`) still blocks on Phase 22 Cohort D #62 per its spec.
