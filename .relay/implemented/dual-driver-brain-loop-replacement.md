# Implemented: Dual-Driver Brain Loop Replacement

## Summary

*Resolved: 2026-05-24*

**Problem**: Phase 22's dual-driver cluster shipped 6 foundation features (#54 orchestrator-core, #55 lead-follow, #57 lead-handoff-reconciliation, #58 backward-transitions-and-substrate-advisory, #60 autonomy-spectrum, #61 halt-categories) but the brain still ran the deterministic-walk model — `src/conductor/loop.ts` spawned a `TaskAgent` per card per iter via `defaultAgentFactory` and TaskAgent ran a hardcoded `switch (column)` policy. The orchestrator-core's `decide()` engine was unconsumed by the loop. Without #59, all 6 foundation features were dead-code-shaped: producer-only (#57 deferred-reconciliation Map), waiting consumer (#60 `effectiveAutonomy` + `autoExecuteThreshold`), or only partially live (#61 typed `HaltCategory` invoked from the existing TaskAgent halt path). The dual-driver model was half-built.

**How it was resolved (the BIG-BANG SWITCH)**: Replaced the internal `runOneCard` of `src/conductor/loop.ts` with an orchestrator-driven sequence — lead-check guard → deferred-reconciliation check (consumes #57's Map) → `decide()` → `executeDecision()` → halt-loop circuit breaker. `ConductorArgs` signature changed (`agentFactory: AgentFactory` → `adapter: ModelAdapter`) but the Conductor class public surface (start/stop/status) is preserved — RPC `conductor_start` is the only production caller, plus 12 test cases in 2 files. New shared `src/conductor/executor.ts` module (~400 lines) is the single dispatch surface for all 7 OrchestratorAction variants (call-op invoking engine/ops/*; advance-column writing frontmatter; halt-with-handoff transferring lead then publishing typed halt; advise publishing observer-advisory; wipe/branch-substrate calling substrate_hygiene primitives in-process; no-op). The executor reads autonomy mode + decision confidence via #60's `effectiveAutonomy` + `autoExecuteThreshold` to gate EXECUTE vs SURFACE_TO_OPERATOR; SURFACE publishes `conductor-pending-decision` + awaits matching `pending-decision-resolved` via a bus-mediated promise (5-minute default timeout, per-mode configurable). Every decision is persisted to `<runId>/orchestrate.md` for audit (the `ArtifactOp` widening from #54 enabled this in advance).

**Halt-loop circuit breaker**: 3 consecutive `halt-with-handoff` decisions on the same card (configurable per-mode via new `autonomy.budgets.<mode>.halt_loop_threshold`) trips a `conductor-halt-loop-detected` event carrying `lastCategory` (typed via #61) and `lastRationale` (from the orchestrator decision) so operator triage doesn't require correlating against preceding halt events — then auto-transfers lead to human.

**Three review-driven fixes** (HIGH-1/2/3 from /relay-review) are first-class:
- HIGH-1 (halt-loop event richness): `conductor-halt-loop-detected` carries `lastCategory: HaltCategory` + `lastRationale: string`.
- HIGH-2 (deferred-reconciliation error handling): on executor or decide() failure within the deferred branch, runOneCard publishes a `conductor-halt` with `reconciliation-failed:` prefix AND preserves the deferred entry so the next iter retries on transient failure.
- HIGH-3 (halt-with-handoff dispatch ordering): the executor's `dispatchHaltWithHandoff` calls `transferLead` FIRST (fail-loud wrap) THEN publishes the conductor-halt — ensures the outer loop's next-iter lead-check guard always fires when transfer succeeds.

**Pattern precedent**: pure-helper extraction + shared-dispatch-module pattern reaches **n=21** (counting executor's 7 dispatch helpers + awaitResolution + persistDecision + modelFor + the new event variants). ADR filing remains operator-deferred per `feedback-adr-scope-discipline.md` memory.

**Architectural impact**: Dual-driver is now real. The brain IS the orchestrator running in a tight iter loop, not the hardcoded TaskAgent column-switch. Phase 29.3's `step_resolver.ts` (the stop-gap that papered over the column-switch's brittleness on the `approved` column) is now orphaned in the brain path — `decide()` produces the next step from substrate naturally via `CallOpParams.step`. See Caveats for the retain decision.

## Caveats

- **`src/conductor/step_resolver.ts` retain decision (the load-bearing trace per dispatch brief)**: KEEP the file. Its sole brain consumer (`defaultAgentFactory`) is gone; in the brain path the orchestrator's `decide()` produces the next step from substrate naturally via `CallOpParams.step` and the executor's `dispatchCallOp:implement` consumes it. BUT: TaskAgent is retained (per design Open Question #3 lean) for the CLI `conductor work` path + RPC `card_work` handler at `src/rpc/methods.ts:197`; TaskAgent's `approved`-column branch still requires a `step` arg. The CLI/RPC path currently passes `step` directly from operator input (no resolver involved); step_resolver was wired ONLY into the brain's defaultAgentFactory IIFE. Post-#59 the module is exported, unit-tested, and used by zero call sites in production code. Removing it cleanly would be a separate cleanup PR; leaving it in place preserves a useful pure helper (plan-substrate parser + git-log diff) that future operator surfaces (e.g., a `card_work` enhancement that defaults the `step` arg from substrate) could consume. Decision: KEEP for v1; flag for a future cleanup pass if no consumer materializes within 1-2 phases. Unit tests at `tests/conductor/step_resolver.test.ts` continue to pass.
- **`bridgeSpectrumToConductMode` left exported but unused by loop.ts**: the brain no longer calls `conduct()` so the bridge is dead code from the brain's perspective. The helper has its own test coverage at `tests/conductor/autonomy.test.ts:115` and is still exported from `src/conductor/autonomy.ts`. Leave in place — TaskAgent's `transitionWithGate` still uses `conduct.ts` indirectly via the legacy autonomy.transitions.* path, so the bridge has potential future consumers (e.g., if `card_work` migrates to spectrum-mode awareness). Cleanup deferred.
- **`brain-cannot-advance-cards-past-approved-column` is now resolved-by-supersession**: the original `--step` halt that surfaced the entire dual-driver brainstorm is naturally resolved by #59. The orchestrator computes `step` from substrate as part of its `call-op:implement` decision; the brain path no longer hits the synthetic halt that the Phase 29.3 stop-gap papered over. The archived issue at `.relay/implemented/brain-cannot-advance-cards-past-approved-column.md` does not need a back-update because the supersession is mechanical (the issue's bug surface — `approved`-column without `--step` halting the brain — no longer exists in the dual-driver model).
- **Pending-decision amend payload deferred to v2**: the `resolution: 'amend'` value is honored by the executor (proceeds with dispatch) but the amended decision payload isn't yet plumbed through. v1 dispatches the ORIGINAL decision on amend. Richer amend semantics belong to feature #62 frame-b-chat-wire (the operator-driven amend surface).
- **Pending-decision listener leak prevention**: `awaitResolution` uses a paired `done` flag + `clearTimeout` + `unsub` cleanup on both the resolve and timeout branches. Tested via the assist-mode timeout + assist-mode approve tests in executor.test.ts.
- **Halt-loop reset semantics**: the counter increments only when `outcome.kind === 'halt-published'` AND same card as last iter AND last iter also halted; it resets to 1 (not 0) on a different-card halt to count the current halt; resets to 0 on any non-halt outcome. This is the wedge-detector-friendly pattern — does not interfere with Phase 27.2's `lastIterationHalted` suppression branch.
- **No persistence across daemon restart for pending-decisions**: per design OQ #4, the executor's `awaitResolution` promise lives in-memory; daemon restart while a pending-decision is in flight loses the wait state. Acceptable for v1 (the next iter re-decides); defer persistence to a follow-up if dogfood surfaces the friction.
- **Brain-loop UI rendering of new events deferred**: `conductor-pending-decision` + `pending-decision-resolved` + `halt-loop-detected` events flow through SSE (DaemonEventKind extended in `src/ui/events.ts`) but no card_detail.ts or monitor.ts handlers render them yet. Deferred per #57 + #58 polish-ticket precedent. Operator can `tail .conductor/brain.log.jsonl` to inspect (brain_log filter `startsWith('conductor-')` auto-persists all three).
- **TaskAgent flake watch**: the known existing flake on `tests/conductor/loop.test.ts > 'Daemon shutdown stops the conductor brain'` (spec OQ #7) did NOT reproduce on the rewrite test pass. The new loop's lifecycle (decide() in-iter, no per-iter TaskAgent spawn) may have eliminated the race condition entirely. Watch for re-occurrence over the next several test runs.
- **`config.confidence.threshold` and `config.autonomy.hybrid_confidence_threshold` both still exist**: per #60's deviation #2 caveat — both kept for backward-compat. The new executor reads `hybrid_confidence_threshold` via `autoExecuteThreshold(mode, config)`. Unification opportunity for v2.
- **`new RoutingAdapter()` in `conductor_start` constructs fresh per start**: minor — previously `defaultAgentFactory` did the same. If daemon-wide adapter sharing becomes important (cost-tracking aggregation), wire `ctx.adapter` upstream. Current behavior matches the pre-#59 baseline.
- **#62 frame-b-chat-wire unblocked**: this feature exports `executeDecision` as the second-consumer surface. Frame B chat (next in the cluster) can now call into the same dispatch table to execute orchestrator decisions surfaced from chat-driven flows. The shared module placement at `src/conductor/executor.ts` is the seam #62's design (`Wire: ## Integration Points`) anticipates.
